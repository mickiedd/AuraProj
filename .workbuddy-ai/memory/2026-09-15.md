### Key facts worth remembering

- The V4 pipeline is a four-script quartet: `PrepareV4Buildings.py` →
  `ImportV4Buildings.py` (per-package `import_package(i)`) → `FinalizeV4BuildingMaterials.py`
  → `ValidateV4Buildings.py`, plus `CaptureV4Buildings.py` for renders. Drivers live in
  `Saved/RawModelImport/V4/` (`import<N>.py`, `remote.py`).
- `Saved/RawModelImport/V4/remote.py` is the generic live-editor runner: it starts a
  Python remote-execution client, waits up to 15 s for a node whose `project_root` is
  `C:/Git/AuraProj/`, and runs a script file with `MODE_EXEC_FILE`.
- UE 5.5's Interchange FBX path silently returns **zero** meshes for this package's ASCII
  FBX. Working around it needed `Interchange.FeatureFlags.Import.FBX 0` plus an explicit
  `unreal.FbxFactory()`. Zhengximen also ships a clean `.glb` sibling that would have
  sidestepped the problem entirely.
- Two gotchas discovered while reading the code, both still unfixed:
  - `create_blueprint` hardcodes `collision = False`, so `UCX_*` collision meshes are
    imported but never attached to any Blueprint (`collision_components` is always 0).
  - `SubobjectDataSubsystem.k2_gather_subobject_data_for_blueprint` returns each
    `StaticMeshComponent` **twice** (1→2, 8→16); the tuning scripts' `assert changed == 2`
    bakes that doubling in.
- `actor.get_actor_bounds()` on these Nanite meshes is unreliable and process-dependent:
  the same validator reports Dadongmen 2248.0 cm in the live editor but 2138.5 cm in a
  headless commandlet. Do not trust it as a height guard.

## Reviewed the V4 result against the reference sheets

Compared the four tuned gates against their reference posters and the source package
previews. Key conclusions:

- **The source geometry is faithful.** `Dadongmen_GreatEastGate_UE5/Previews/02_Front_Elevation.png`
  shows the full massing (battered wall, arch, two-storey pavilion, double-eave roof,
  balcony, lattice windows). The 3/4 clay preview hides the pavilion and is misleading —
  use the front elevation preview when judging massing.
- **The tuning inverted the tone.** Every tuned material is
  `BaseColor = tex_BC × Constant3Vector(tint)` with tints around 0.28–0.78. Multiplying a
  mid-grey constant into an already-correct albedo halves brightness and crushes contrast,
  which is why all four roofs read black and the walls read as flat slabs. This is the
  single highest-value thing to fix.
- **Reference images live in `%TEMP%`** as `codex-clipboard-*.png`; the four V4 ones are
  `5ea059eb…` Dadongmen, `58990fa0…` Guidemen, `c9737a14…` Wuxianmen, `f1f30b9a…`
  Zhengximen. They are purgeable, so they should be copied into the project.
- Worst visible defects: detached green vegetation shards on Dadongmen and two floating
  objects over Wuxianmen; dense horizontal stripe banding on Zhengximen's wall; an
  obvious repeating texture grid on Wuxianmen's wall; an illegible 歸德 inscription.
- `TuneDadongmenDoorDetail.py`'s `hide_source_ground_material()` deletes every expression
  from the tuned Dirt/Water materials and forces opacity 0 — hide the components instead.
  The same script reports `geometry_changed: false` while adding ~50 components.
- Codex spent 07:24–08:38 in a non-converging capture-framing loop (~20 `CaptureDadongmen*`
  scripts). The capture harness needs a fixed transform + FOV and one screenshot per
  process.

### Quantitative tone-gap measurement

`Saved/RawModelImport/V4/analyze_tone_gap.py` (Pillow, read-only) masks to *textured
surface* pixels — local deviation ≥ 6 grey levels after a radius-2 box blur — because a
plain crop average is dominated by the render's smooth sky gradient and flat ground plane.
Results written to `Saved/RawModelImport/V4/tone-gap-analysis.json`.

Surface mean and contrast, close-up vs reference hero:

| Building | mean ratio | contrast ratio |
|---|---|---|
| Dadongmen | **0.49×** | **0.50×** |
| Guidemen | 0.79× | 0.82× |
| Wuxianmen | 0.96× | 0.71× |
| Zhengximen | 0.81× | 0.83× |

All four renders are darker and flatter than their references; Dadongmen is at half
brightness and half contrast. Textured-surface fraction is 16–25 % in renders against
65–74 % in references, though that column is directional only because the reference crops
include highly textured street scene, boats and foliage.

**Lesson worth keeping:** never judge these renders from a plain crop average — the
background plane dominates it. Mask by local variance first.

## Switched the render adapter back to the Tesla P40 (and found a silent degradation)

The user asked to switch rendering to the P40. It turned out the editor had **already**
been on the P40 up to the 2026-09-14 07:35 session, then silently fell back to the Intel
iGPU for the session that started 00:18 today (machine booted 00:15; the editor started
~3 min later, before the P40 was enumerable).

Key facts worth remembering:

- UE 5.5 picks its D3D12 adapter with `IDXGIFactory6::EnumAdapterByGpuPreference(...,
  DXGI_GPU_PREFERENCE_HIGH_PERFORMANCE)`, then prefers the non-integrated non-WARP adapter
  with the largest dedicated VRAM. On this box that is always the P40 (24268 MB vs the
  Intel iGPU's 128 MB), so **no override is needed and the default rule is already right**.
- **The failure is silent and expensive.** The Intel iGPU reports
  `AtomicInt64OnTypedResourceSupported = false`; UE requires that for its D3D12/SM6 path,
  so it computes SM5, rejects D3D12/SM6 and drops the **whole engine** to D3D11/SM5 with
  **Nanite and Lumen disabled**. The 00:18 log has 166 `UseNanite(PCD3D_SM5) returned false`.
- Diagnostic recipe that worked: grep `Saved/Logs/*.log` for `Found D3D12 adapter`,
  `Chosen D3D12 Adapter Id`, `RHI D3D12 with Feature Level SM6 is supported` and
  `attempting to fall back to RHI D3D11`. UE logs in **UTC** while the log file header is
  local (UTC+8) — easy to misread the session time by 8 hours.
- Vtable slots matter and should be counted, not guessed: `EnumAdapterByGpuPreference` is
  slot 29 of `IDXGIFactory6` and `CheckFeatureSupport` is slot 13 of `ID3D12Device`
  (Windows SDK 10.0.22621.0).
- A probe using the system `d3d12.dll` reports shader model 6.6 where UE (bundling a newer
  Agility SDK) reports 6.7. The decisive gate is atomic64, which agrees.
- **Launching a persistent GUI process from a tool call does not work here** — spawned
  children are reaped when the call returns (`Start-Process`, `cmd start`, and an
  `explorer.exe` handoff all failed; WMI `Win32_Process.Create` is blocked). Registering
  and running a **scheduled task** does work, and the task can be unregistered immediately
  afterwards while the editor keeps running.
- **Earlier visual QA is confounded:** every V4 landmark capture from 01:04–07:15 today was
  rendered with Nanite and Lumen off. The "roofs read black / walls read as flat slabs"
  conclusion in `2026-09-15-v4-reference-conformance-review.md` is exactly the no-Lumen,
  no-Nanite symptom and should be re-checked on fresh P40 captures.
- `nvidia-smi` fails with `Failed to initialize NVML: Unknown Error` while the card is fine
  for D3D12. Versions match (`nvml.dll`/`nvidia-smi.exe` 8.17.15.3867 vs driver
  31.0.15.3867). The installed package is the **vGPU/GRID-class driver** — bound from
  `nv_dispwi.inf` with `nv_*_VGPU_copyfiles` sections and `GridLicensedFeatures = 7`, and
  no `GridLicensing` key or `nvidia-gridd` service. NVML in that line expects a vGPU
  licence a bare-metal P40 does not have. Swapping to the standard Data Center/Tesla
  graphics driver is the fix and is **not done yet**.
