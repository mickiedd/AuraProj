## Wenmingmen facing corrected in the showcase ring

Continues the 2026-09-24 session (started 23:44). User asked to place `BP_Wenmingmen`
in `L_GuangzhouLandmarkShowcase` "with a reasonable position". It was **already**
placed (registered and rebuilt 2026-09-24), so the job became verifying the position.

It was wrong: the gate stood **back to front**. With `facing_offset 0.0` its facade
pointed away from the plaza, so the viewer saw the blank rear wall and its own
per-landmark accent light lit that rear wall.

### The finding

The 2026-09-24 placement claimed Wenmingmen "follows the same local -Y front
convention as the other gates". Never measured, and false. Four readings on the
placed actor, in its own frame, put the facade on local **+Y**:

- `SMC_water` (canal the bridge crosses) — local Y **710..1810**
- `SMC_iron` (door ironwork) — thin plate at **~200**
- `SMC_foliage` (vines) — band at **~200**
- `SMC_stone`/`SMC_limestone` (paved platform) — start at **~-230**, run to **+1867/+2351**

The canal reading is load-bearing because it is **rotation-invariant**:
`Saved/Reports/Wenmingmen/final-front.png` shows the closed timber door, couplets and
vines on the same side of the model as the bridge and canal, so the door is on +Y
whatever the preview axes are. Plaza side is local -Y (the light is built on the
plaza side and measured local Y -5248).

### Measurement trap worth remembering

Wenmingmen's six components are plain `StaticMeshComponent`s with a **-90° component
rotation** (Z-up GLB import), not HISM. So `relative_location + mesh bounds Z` is wrong
by a whole axis — it claimed a local Z floor of -2351 cm where the truth is -332.5, a
20 m error that reads exactly like a sunken building. Correct route: transform the mesh
bounds corners through each component's `get_world_transform()`; it reproduced the
Blueprint bounds (6500 × 2806.90 × 2199.01) exactly. `PrimitiveComponent.bounds` is not
exposed to Python; `get_editor_property("relative_transform")` raises on these components.

**Consequence for the 2026-09-24 caveat**: the gate does **not** float 332.5 cm above the
plaza. Its rendered geometry spans world Z 0.0..2199.01, so the stone base sits exactly on
the plaza; 332.5 is the actor origin. Its canal water sits at world Z ~48.5-56.5.

## Zhengximen / Great West Gate imported as a landmark Blueprint — the 8th landmark

Closes the "queued as the 8th landmark" item above. User supplied
`Zhengximen_GreatWestGate_UE5_Package.zip` (244 MB, 93 files) plus a reference board and
asked for it **as a building blueprint**, then confirmed it should also join the ring.

**Zhengximen did not previously exist in the project.** `find Content -iname "*Zhengximen*"`
returned nothing. The old `Scripts/ImportAndPlaceGreatWestGate.py` is a Windows-era script
pointing at `C:/Works/Raw3DModels/SM_Zhengximen_GreatWestGate_5M_PBR.glb`, a different level
(`L_showcase_level`) and a 20-part 5.7M-triangle source — none of which exists here, so it
was never the precedent it looks like.

Delivered: `Content/Assets/Environment/GuangzhouLandmarks/Zhengximen/` — 7 meshes,
`M_Zhengximen_Master` + 8 `MI_*`, 48 4096² textures, `BP_Zhengximen` (PackedLevelActor,
**7 HISMs** on a `LevelInstanceComponent` root). Spawns at **5320 × 1080 × 1689.68 cm**
(the package's declared 53.2 × 10.8 × 16.9 m) with **206,252 triangles — the declared LOD0
count exactly**.

### The two findings that decided the route

1. **The package's own documented import path does not work here.** `SM_Zhengximen_LOD0.fbx`
   — the only variant carrying UCX collision and the UV1 lightmap atlas — was probed twice:
   legacy `AssetImportTask` + `FbxImportUI`, and `InterchangeManager.import_asset` with an
   explicit `InterchangeGenericAssetsPipeline`. **Both times Interchange logged
   `start importing source [...LOD0.fbx]` and never the matching `completed` line** — no
   asset, no error, no traceback — while four GLB imports succeeded in the same run. So the
   FBX is a dead end in this build, and that is a general trap: **a silent non-completion,
   not a failure you can catch.**
2. **`SM_Zhengximen_LOD0.glb` has `"materials": []`.** A combined GLB import would give ONE
   material slot for the whole gate. Hence the **per-material modular GLBs**, one mesh per
   material group, one slot each — binding by construction, no slot-name matching.

Cost of skipping the FBX: no UCX collision, no UV1 atlas. Collision is rebuilt as
`CTF_USE_COMPLEX_AS_SIMPLE` on the five structural groups, exactly as `ImportWenmingmen.py`
does; the project lights with Lumen so the atlas is not on the critical path.

### The orientation trap — and why the first heuristic failed

The GLBs are **trimesh** output with **Z-up** POSITION values, against glTF's Y-up
convention, so Interchange tips them over. At **roll 0 every group comes back with Y and Z
transposed** — AgedWood's 18.86 × 8.64 × 14.70 m arrives as 18.86 × 14.70 × 8.64. **Roll
−90 restores the source exactly**, and **scale 1.0 is correct** because Interchange already
converts the glTF metres to centimetres. (Same `IMPORT_ROLL = -90.0` as
`ImportGreatNorthGateHighDetail.py`.)

**My first importer accepted two groups transposed** because it tested "Z exceeds Y" plus a
plausible X band. That test is simply wrong for this model: the brick wall is genuinely
1000 cm deep and 870 cm tall, and the timber band 818 deep and 675 tall — so "height exceeds
depth" is false for correctly-oriented parts and true for transposed ones. **The fix that
generalises: judge each group against its own GLB POSITION accessor bounds** (read min/max
from the glTF JSON) within 2%. All seven then resolved to roll −90 / scale 1.0, first
candidate. Do not use axis heuristics for orientation on multi-part buildings.

### Other deliberate choices

- **Normals NOT flipped.** The package is DirectX (Y−), which is what Unreal expects;
  `flip_green_channel` exists to convert OpenGL and would have inverted every normal. Note
  this is the **opposite** of `ImportWenmingmen.py`, whose source genuinely was OpenGL.
- **Nanite fallback forced to the full mesh** (`PERCENT_TRIANGLES` 1.0, relative error 0.0)
  — `AUTO` decimates on Metal and renders black holes.
- **All paths project-relative** from `unreal.Paths.project_dir()`. The package's own
  `Unreal/*.py` helpers hardcode `/Game/Zhengximen` and derive their root from `__file__`.

### Two bugs the run found in my own validator

- A material-path check used `endswith("/MI_<group>")`, but the real path is
  `.../Materials/MI_GrayBrick.MI_GrayBrick` — match on `"/MI_<group>."` instead.
- A per-part "lying on its side" assertion (`size_z > size_y`) — **wrong in principle**, per
  the wall/timber sizes above. Removed; orientation is guarded by the union footprint.
- Also: `unreal.MaterialEditingLibrary.get_material_instance_parent` **does not exist**; read
  `instance.get_editor_property("parent")`.

### Commandlet / API traps hit

- **`print()` never reaches a commandlet's captured stdout**, and neither does `unreal.log`
  reliably — write a **JSON report** and read that. I lost a whole probe run to this.
- **`k2_gather_subobject_data_for_blueprint`** — "**for**", not "from". A typo cost one run.
- `unreal.EditorStaticMeshLibrary.get_lod_count` / `get_simple_collision_count` are deprecated
  but still work.
- A partially-created Blueprint is **saved before its components are added**, so a crashed run
  leaves a wrapper that looks real and has none of the building. The reuse path must **verify
  the HISM count and rebuild** rather than trust the asset's existence.
