# 2026-09-21

## Guangzhou landmark showcase level

User asked for a new level gathering all landmarks from
`Content/Assets/Environment/GuangzhouLandmarks`, then (before building it) asked to
wrap the landmarks that were not yet independent Blueprints into building Blueprints.

### Decisions taken with the user

- **Wrap scope**: GreatNorthGate (Dabeimen) + ZhenhaiTower only. The legacy
  `Xiaobeimen/SM_Xiaobeimen` and `SM_Xiaobeimen_GeometryFixed` meshes were left alone —
  that gate already has two V3 Blueprints, so wrapping them adds a third Xiaobeimen.
- **Layout**: ring around a central plaza, each landmark turned to face the centre.
- **Level path**: `Content/Assets/Environment/GuangzhouLandmarks/L_GuangzhouLandmarkShowcase`
  (inside the landmark folder, matching the per-landmark `_Preview` maps).

### What was built

- `GreatNorthGate/BP_GreatNorthGate` and `ZhenhaiTower/BP_ZhenhaiTower` — PackedLevelActor
  Blueprints, one HISM each, one instance at identity. Footprints match their source
  meshes to 0.0 cm (3600×1750 and 3466.6×2834.6).
- `L_GuangzhouLandmarkShowcase` — 9 landmarks in a ring of radius 10612.12 cm, 420 m
  ground plane, preview-style lighting, 9 text labels, PlayerStart. 25 actors total.
- `M_ShowcaseGround` — neutral dark paving material (base colour 0.165, roughness 0.88).

### Traps found (now in the `unreal-level-build-and-place` skill)

1. **`unreal.Rotator` positional order is `(roll, pitch, yaw)`, not `(pitch, yaw, roll)`.**
   `Rotator(0.0, yaw, 0.0)` sets **pitch**. The first build produced a ring of landmarks
   tipped on their sides, and `get_actor_bounds` reported Guidemen as 5730 cm tall —
   which I initially misread as a corrupt asset. Use keyword arguments.
2. **Hidden `Collision_UCX_*` volumes sit exactly 128 cm below the actor origin on all
   nine landmarks**, so `get_actor_bounds` reads every correctly grounded landmark as
   sunk ~1 m. Ground and space from instanced mesh data, skipping non-rendering components.
3. **`BlueprintEditorLibrary.compile_blueprint` returns `None`** in this build (void, not
   bool) — asserting on it fails on success. This had a real consequence: the assert
   aborted the first run *after* the asset was created but *before* it was saved, so
   `BP_GreatNorthGate` existed only in the editor's memory — the registry resolved it, the
   level referenced it, spawning worked, but there was no `.uasset` on disk and it would
   have been lost on an editor restart. Caught by listing the folder. The wrap script now
   saves on its reuse path too and asserts the `.uasset` exists on disk (32,723 and
   32,813 bytes confirmed). **Lesson: an asset that resolves in the editor is not
   necessarily an asset that exists on disk — check the folder.**
4. **HISM derives from StaticMeshComponent**, so querying both classes double-counts every
   HISM. Query `StaticMeshComponent` alone.
5. **`relative_transform` is unreliable on the V3 Blueprints** — it returns a rotation that
   turns the local Z range into the Y range. Use `relative_location` (translation only);
   these components carry no relative rotation.

### Validation

`Scripts/ValidateGuangzhouLandmarkShowcase.py` reloads the saved level from disk:
**0 errors, 0 warnings** — 9/9 landmarks exactly once, actor Z within 0.004 cm of the
placement manifest, 0 XY overlaps, all inside the ground plane, ring radii
106.12–115.94 m with 32.9°–47.1° angular gaps and full 360° coverage.

Component/instance counts for the seven pre-existing Blueprints match the project's own
recorded figures (Guidemen 47/18822, Zhengnanmen HighFidelity 114/12383, Wuxianmen
7/5103 each, Xiaobeimen 51 and 16, Zhengnanmen AAA V3 25), confirming placement did not
alter the assets.

### Lighting — a wrong diagnosis, corrected

I first concluded the captures rendered the scene **unlit** (the ground appeared to draw
at exactly its own base colour, and hiding every light including the key left the image
byte-identical). **That was wrong on two counts:**

1. **Hiding a light actor does not disable the light.** `set_actor_hidden_in_game` does
   not stop a `LightComponent` contributing, so the test returns an identical image
   whether the scene is lit or not. It proves nothing.
2. The scene is **lit but severely over-exposed** — bright surfaces clip to white, dark
   ones to black, which is what produced the bimodal histograms.

Confirmed by bracketing exposure with a temporary unbound post-process volume and
looking at the images: at EV100 3.0 the gate is legible (stone + coursing, dark arch, red
beams, gold ridge) but the stone still clips; at 4.0 the stone reads correctly but the
frame goes dark.

Two things rule the level out as the cause:

- The project's own `L_Xiaobeimen_AAA_V3_Preview` renders identically washed out under
  the same capture setup, and framing the *same asset* in both levels gives comparable
  histograms (4.1/4.6/85.9 vs 9.0/0.9/89.3). The showcase recipe (key 7.0, fill 2.0, sky
  1.4, atmosphere) matches the preview levels' (8.0/2.0/1.4/atmosphere).
- The harness is not reproducible: identical settings give different renders between
  runs, and the level's own unbound PPV does not reproduce the bracketed value while a
  runtime PPV at higher priority does.

**Resolution:** the level pins exposure at EV100 3.0 rather than copying the preview
levels' 1.0, and the capture script pins the same value so captures are deterministic.
Layout is confirmed visually; lighting is confirmed correct by the bracket images
(`ev-{20,30,40,50}.png`) but should be eyeballed once in the editor, since single-frame
captures cannot reproduce converged auto-exposure or the temporal sky sampling.
