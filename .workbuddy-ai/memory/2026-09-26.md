## Zhengdongmen roof ridges given their own material

Follow-up to yesterday's roof-course work. User, from a viewport screenshot of
`BP_Zhengdongmen`: "the 屋脊 parts of the roof should use different textures."

### What was actually wrong — two things, and the second was the worse one

1. **The ridges shared the `RoofTile` material.** The 正脊, all eight 垂脊 hip beams and all
   eight 翼角 eave-corner beams were `beam('RoofTile', ...)`, so a hip cap carried a
   corrugated tile field along its length and read as a continuation of the roof.
2. **`beam()` gave every beam a world-space XZ planar UV.** On a diagonal hip the tile
   field's ribs and courses smeared *across* the cap instead of running down it. That is
   what the screenshot showed as a thin dark smear.

### The fix

- New **`Ridge` material group**; the package has no artwork for it, so the whole set is
  authored (`Scripts/MakeZhengdongmenRidgeTextures.py`).
- New **`ridge_beam`** sweeps a half-round 脊瓦 section (flat base + semicircle) instead of a
  square tube. Sized to **fill the same bounding box** — semicircle of radius `width/2` on a
  `width/2` base — so the envelope does not move. Confirmed: the Ridge part measures
  **2697.36 × 1408.97 × 722.15 cm, identical to the old RoofTile box**, and the union is
  still 2870 × 1639 × 1933.12.
- UVs **along the ridge on u** (1.5 m/repeat), **once around the section on v**; `beam()`
  gained the same `uv='axis'` mode. Its section "up" is now kept pointing up — flipping both
  section axes leaves the eight corners in the same places, so **it changes no geometry**, but
  without it the horizontal ridge beams had "up" pointing *down*.
- Texture: 1024 × 512, four ridge-tile joints per repeat (one every 0.375 m), weathering
  shaded across the section with the crest at v 0.66. It does **not** paint a second crown —
  the geometry has one, and doubling a modelled profile is the defect this project keeps
  hitting.

### Three traps, all new

- **A new material group has no material instance.** The apply path reimported meshes and
  rebound components, but material instances are built by `ImportZhengdongmenLandmark.py`'s
  own `main()`, which `ApplyZhengdongmenReference.py` never runs — so `MI_Ridge` did not
  exist and the Ridge mesh could not be bound. Fix: call the import's **idempotent
  `build_instances(master)`**, which creates the missing instance and re-binds every group.
- **A swept beam's end caps need explicit UVs.** A ridge beam's caps are perpendicular to its
  axis, so the default world-XZ projection gave every one of their vertices the same `u`:
  the engine reported *"degenerate tangent bases which will result in incorrect shading"* and
  *"nearly zero bi-normals"*. A planar UV in the section's own plane took it from 2 warnings
  to 0.
- **Migrate a Blueprint in place when a level references its class.**
  `CreateZhengdongmenLandmarkBlueprint.py` sees the 7-vs-8 HISM count and
  **force-deletes then recreates** the asset; `L_GuangzhouLandmarkShowcase` holds a reference
  to `BP_Zhengdongmen`'s generated class. `ApplyZhengdongmenReference.py` now **adds the
  missing HISM to the existing asset** instead, so the identity survives.

### Verification

- Preflight: 8 parts, union unchanged to the centimetre.
- Roof-tiling validator: passes; the courses are untouched.
- Landmark validation, fresh process: **0 errors / 0 warnings**, **8/8 parts** matching the
  tuned source exactly (Ridge 680 triangles), `MI_Ridge` bound with all five maps.
- Gate **337,154 → 337,630 triangles** (RoofTile 289,852 → 289,648, Ridge 680).
- Eight native Metal captures including a new straight-on ridge view; cleanup 0 → 0.

### Open

- No ridge ornaments (脊兽 / 吻兽). The reference render shows small finials at the main-ridge
  ends and the corners; the ask was textures, so none were added. Worth asking before adding,
  since it is a geometry change and would move the envelope.
- `Raw3DPacket/Zhengdongmen/` is still uncommitted.

## Zhengdongmen top roof: the "hollows" were a flat top, not a tiling bug

User, from a viewport screenshot looking down the upper roof: "fix the hollows on the top roof
side."

### What it was

Not a tiling problem at all. The two north/south slopes of the upper roof started at
**y = ±0.5 m** instead of meeting at the ridge, so the top of the roof was a **1.0 m wide flat
band** of bare substrate — and the 0.30 m ridge cap covered only its middle, leaving **0.35 m of
bare substrate exposed on each side**. A 庑殿 hip roof's ridge is a *line*.

### The fix

Slopes now meet at **y = 0**. Three consequences, all corrections:
- courses run right up to the cap on both sides;
- the east/west faces become **true triangles** rising to the ridge ends (`half_width_at(0)`
  0.5 → 0);
- the hip caps start on the ridge line, so the three caps converge at the apex instead of
  leaving a notch.

### The lesson is about the views, not the geometry

Course continuity and the ridge material were both verified with **straight-on** views, and
**neither can see a band along the ridge** — it is only visible looking *down* the roof. A new
`roof-ridge` view (camera above and off one end, aimed along the ridge) went into **both**
`RenderZhengdongmenPreviews.py` and `CaptureZhengdongmenReference.py`, and it reproduced the
user's viewport exactly. That is what made the cause unambiguous instead of a guess.

**Generalise it: every fix so far has been verified from a view that could not have shown the
next defect.** When a user reports something from an angle you have never rendered, add that
angle to the renderer and the capture before diagnosing.

### Numbers

Upper N/S slope length 5.25 → **5.72 m**; courses 16 → 17; tiles 3,448 → 3,528; roof tile mesh
289,648 → **296,030 tris**; gate 337,630 → **344,012**. Widest uncovered strip on the upper
east/west faces 0.0124 → **0.0000 m** (they taper to a point now). Envelope
**2870 × 1639 × 1933.24 cm** (+0.12 cm — the hip caps shifted a hair as the hip line moved; the
ridge cap still sets the height). Validators: roof tiling pass, GLB preflight pass, landmark
**0 errors / 0 warnings** with **8/8 parts** exact. **9 native captures**, cleanup 0 → 0.

### Process failure, and the guard it produced

**A GUI editor was open when the reimport commandlet ran.** The disk assets came out correct and
the fresh validator confirms them, but the editor held stale copies of `SM_ZDM_RoofTile` and
`BP_Zhengdongmen` until the user closed it. The check was in the earlier run of this session and
was simply missing from this one. `ApplyZhengdongmenReference.py` now **refuses to run** while a
GUI editor holds the project:

```python
subprocess.run(['pgrep', '-f', r'UnrealEditor\.app'], ...)
```

The `.app` is load-bearing: the script runs as `UnrealEditor-Cmd`, which also contains
"UnrealEditor", so a bare pattern matches the commandlet itself and always fires. Verified: the
guard passes cleanly with no editor, and the pattern matches the real editor's observed command
line (`.../UnrealEditor.app/Contents/MacOS/UnrealEditor <project>`). The sandbox here blocks
spawning a process with that name, so the *firing* path is reasoned from those two observed
command lines rather than reproduced.
