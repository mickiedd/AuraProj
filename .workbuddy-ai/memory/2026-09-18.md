(`num_custom_data_floats`), by the variation of the source data, and by the write
counts recorded in the apply report.

## Guidemen V5 4K roof-shell inversion corrected (user caught it, I missed it)

The user reported Guidemen's roof was **still inverted** after my cross-building pass
concluded it was correct. **They were right; I was wrong.**

**The mistake:** my probe correlated top-surface Z against distance from the *whole
roof group's* centre and read a clean fall (2,002 cm centre to 1,465 cm perimeter).
That is confounded on a **two-tier** roof - the upper tier sits near the centre and
higher, the lower tier reaches further out and lower - so the aggregate falls with
radius *even when each tier's slope is inverted*. A cross-tier correlation is not a
roof test. Measure per tier, per roof group.

**What actually found it: the ridge-bar anchor.** A ridge bar must cap the highest
line. Guidemen's ridge bars sit exactly on their tier's tile apex and the tiles rise to
that apex, so tiles and ridges agree with each other - but the eight roof shells did
not, sitting **342 cm above the tiles at the eaves**. Sheathing cannot sit above its
own tiles. When a slope cannot be measured directly, use the ridge bar as the anchor.

**Fix:** each shell was flipped in Z about its own ridge-side edge. Applied a 180°
rotation about world X through the pivot `(y=0, z=that shell's minimum Z)` - a rotation,
not a mirror, so winding and normals survive. Front/back and left/right are mirror pairs
about y=0, so the incidental y flip maps each onto its partner's footprint exactly.
**8 of 18,822 transforms changed, 39 components byte-identical.** Each shell now sits
under its tiles with a uniform 9.89 / 9.86 cm clearance on both tiers.

**Measurement limits found on Guidemen's shells:**
- the shell meshes are **not world-aligned** - each shell's local +Z maps to a world
  horizontal axis (front -Y, back +Y, left -X, right +X), so an orientation-based slope
  test is invalid on them;
- **vertex readback is blocked**: `StaticMesh.get_static_mesh_description(0)` works
  (1,568 verts / 2,970 tris for a shell) but `get_vertex_position` needs a `VertexID`
  that cannot be constructed from Python (`unreal.VertexID` exists but its `id`
  property is not settable);
- the tile-normal test was **misleading** (reported a correct 36-42° outward tilt); the
  tile Z range over the slope (180 cm over 565 cm = 17.7°) matching the shell pitch
  (16.9°) is the reliable figure.

## Guidemen isolated slope measurement — five measurement routes blocked, one that works

After the roof-shell fix the user sent a screenshot suggesting the roof still reads as a
valley. No asset changed; this was measurement.

**Five routes are blocked on these roof meshes - do not retry them:**
1. instance AABBs are **sign-blind** - a Z range cannot say which end is high;
2. the shell meshes are **not world-aligned** (each local +Z maps to a world horizontal
   axis), so the instance rotation says nothing about the slope;
3. **vertex readback is blocked** - `get_static_mesh_description(0)` works and reports
   counts, but `get_vertex_position` needs a `VertexID` that cannot be constructed
   (`unreal.VertexID` exists; its `id` property is not settable);
4. **`HitResult` fields are protected** (`location` and `component` both refuse to read),
   so the obvious raycast route dies at the last step;
5. the tile component is **shared by both tiers** (`R1_T0` = 16,248 instances across R1
   and R2), so hiding it isolates neither tier.

**What works:** disable collision on every other roof component
(`set_collision_enabled(NO_COLLISION)` - note **visibility does not affect traces**),
then find the target surface's Z by **bisecting a line trace on the boolean alone**
(18 iterations → 0.01 cm). No HitResult fields, no geometry access.

**Results:**
- All four isolatable shells now **fall monotonically away from the ridge line**
  (Back shells with |y|, Right shells with |x|) - so the shell fix is correct and stays.
  Front/Left return no hit because the fix maps each onto its mirror partner's footprint.
- The tile surface is **flat (~1852 cm) along y at x=0** while the R2 shell under it falls
  137 cm over the same span → on the upper tier **the tiles do not lie on the shells**.
- Three surfaces disagree: shells imply a ridge along **X**, tiles along **Y**, ridge bars
  along **X**. Two of three plus the 31.2 x 11.3 m pavilion proportion say X. The tile
  component is the outlier and is the one that could not be isolated cleanly.

**Owed:** a top-down view and a front/side elevation would settle the ridge axis in
seconds - the capture harness is still broken, so a user screenshot is currently the only
rendering evidence on this project.

## INCIDENT — I crashed the shared Unreal Editor (OOM), and the rebuild pivots

While starting the Guidemen from-scratch rebuild I re-imported the source GLB and **crashed
the shared Unreal Editor** with a fatal out-of-memory error at 14:34:36.

**Cause:** `bake_meshes = True`. The build report says this GLB is *"shared high-detail mesh
instancing"* — **169,891,784 expanded triangles against only 38,276 unique**. Baking writes
each of the 18,823 nodes out as its own mesh, so the import tried to materialise the whole
expanded count and exhausted the paging file ("The paging file is too small"). For these
instanced V5 GLBs: **`bake_meshes` must be False**, and `combine_static_meshes` must stay
False so instancing survives. **Never assume an import is cheap because the file is small** —
74.8 MB on disk was 169.9M expanded triangles. Read the build report or the GLB's own
node/geometry counts and compute the expansion *before* importing.

**Damage: none.** Verified after the crash: `BP_Guidemen_V5_4K.uasset` intact (21:39, includes
the shell correction); the new recovery copy `BP_Guidemen_V5_4K_PreRebuild_20260918.uasset`
intact (22:16); the `_RefTune4` materials intact (21:29); `.../Guidemen_4K/Rebuild20260918/`
never written, so no partial assets. The editor is down and needs restarting.

`Scripts/RebuildGuidemenStep1Import.py` is fixed (`bake_meshes=False`) and now **refuses to
run** if the projected expansion exceeds 20M triangles, with the reason in the assertion. It
carries a DO-NOT-RUN-AS-WRITTEN banner pointing at the record.

**Approach pivoted — a scene re-import is the wrong tool.** The asset already matches the
source exactly (47 components, 18,822 instances, geometry names and node transforms all
corresponding; ridge along X confirmed three ways in the source; the eight inverted shells
already corrected to within 2 cm of the source's own tile span). So the rebuild should
rebuild **the assembly from the source node transforms**, reusing the already-imported
meshes — no heavy import, no OOM risk — applying the shell correction and then the reference
tuning. That is exactly the part that has been wrong across four passes.

**Revised rebuild plan:** (1) read the 18,823 nodes from the GLB JSON chunk + accessors, no
geometry decode; (2) write the component/instance payload onto a rebuilt Blueprint;
(3) apply the shell correction in the pipeline (user's choice of option 1) with the verified

## Guidemen assembly verified against the source — NO REBUILD NEEDED

Checked the two things that would justify a from-scratch rebuild. Neither held.

**1. The meshes are already imported.** `Meshes/Source/` and `Meshes/UprightSource/` each hold
**48 assets** — one per source geometry definition. Nothing to re-import, which also removes
the OOM risk that crashed the editor on the one attempt.

**2. The assembly already IS the source.** All 47 components and 18,822 instances compared as
position multisets against transforms composed from the source GLB's own node hierarchy:

| check | result |
| --- | --- |
| instance counts | **0 mismatches** across all 47 components |
| positions within 1.0 cm | **18,820 of 18,822** |
| single-instance parts | every one at exactly **0.000 cm** — both ridge bars, all 8 roof shells, both piers, arch vault + spandrel, parapets, wings, pavilion floors, and all **16,248 roof tiles** |

**My error, not the asset's.** The first pass used `UE = (x, −z, y) × 100` and reported 2,296
mismatches with 35–852 cm residuals. I nearly read that as an asset defect. The correct
conversion is **`UE = (x, +z, y) × 100`** — proven by testing both per component:

```
SB_0  1806 blocks     (x,-z,y): 0     (x,+z,y): 1804
BA_0   182 brackets               86              182
BB_0   182 brackets               86              182
RP_0    53 posts                   0               53
```

**Lesson: never infer an axis sign from an assembled extent** — magnitudes cannot distinguish
±. Parts symmetric in the ambiguous axis match under either sign, which is exactly why only
*some* components failed and the pattern looked like a real defect. Test both signs per
component and let the asymmetric ones decide.

**Also:** verify an assembly by multiset-comparing instance positions (sort both lists,
compare element-wise — O(n log n)). A greedy nearest-neighbour match is quadratic and does not
finish on a 16,248-instance group; my first attempt was SIGTERM'd.

**State:** the source's own shell defect remains corrected (world Z 1290–1462 / 1708–1855,
clearance 9.89 / 9.86 cm) and survived the crash; tiles untouched and matching the source to
the centimetre; RefTune4 materials and the Nanite fix intact; recovery copy
`BP_Guidemen_V5_4K_PreRebuild_20260918` in place. **No re-import, no rebuild, no destructive
edit.**

**Still missing:** any picture. The capture harness has been broken for five passes, so all of
this is geometry. A top-down view and a front/side elevation would close it.

## Guidemen rebuild — THE CAPTURE HARNESS IS FIXED (after five passes blind)

**The working capture path** — bypasses the editor viewport entirely:

```
SceneCapture2D -> persistent TextureRenderTarget2D
              -> RenderingLibrary.read_render_target(world, rt, True)   # Array[Color]
              -> binary PPM (P6) written from the editor
              -> PNG converted outside the editor
```

Three hard-won facts:
- **`export_render_target` writes NOTHING in this build**, even with a persistent target — that
  is why the earlier attempt at this route produced no file.
- **The editor's Python has NO numpy and NO PIL.** Pixels must go out as a raw format (PPM P6)
  and be converted by the local py310 interpreter.
- `set_visibility(False)` does **not** affect traces or captures; collision does.

Verified by successive views now differing (hero 0.806, front 0.779, side 0.789, top 0.885)
where before every view was byte-similar.

**It immediately exposed: EVERY capture had been showing TWO overlapping Guidemen actors** —
a stale `BP_Guidemen_V5_4K_C_0` from an earlier staged setup plus the current one; the level
held 16 actors. That would have invalidated any material or geometry diagnosis. **The staged
harness leaves actors in the world by design, so a leaked setup is silent and poisons every
later capture — always list the level actors before trusting an image.** Level now cleaned to 0.

**Materials rebuilt (47 slots).** The capture showed most of the building rendering saturated
blue with relief — a normal map read as base colour. Only the two materials rebuilt earlier
(stone, tile) were correct, which was the tell. Ten `*_Rebuild20260918` materials with
`BaseColor->BaseColor (sRGB)`, `Normal->Normal`, `MR.G->Roughness`, `MR.B->Metallic`,
`AO.R->AO`; old graphs kept for rollback. Checked first and both are sound: the source JPGs
(timber 0.397/0.249/0.157 brown; normals 0.498/0.498/0.99) and the imported UE textures
(BaseColor TC_DEFAULT + sRGB on; Normal TC_NORMALMAP + sRGB off; MR/AO TC_MASKS).

**The roof reads correctly from above** — the top-down view shows a clean hip-roof plan: the
ridge along X with the four hip lines running diagonally to the corners. **The X/bowtie pattern
is the hip lines, not a valley** — exactly what a 庑殿 roof looks like from directly overhead.

**STILL OPEN — the blue timber.** With a single actor and fully rebuilt materials the timber,
columns and gate doors still render saturated blue. Ruled out: material wiring (rebuilt),
source maps (correct), imported textures (sRGB/compression/size correct), stale actor (level
cleaned), **and the material at all** — a flat mid-grey on all 47 slots left the stone, roof and
crenellations grey while the timber stayed blue. That points at those **meshes**, most likely
vertex colour or a per-mesh override. Next: hide component groups by collision and capture,
which will name the blue geometry outright.
